# 增量索引与分层缓存

## 1. 为什么需要增量

个人知识库的特点是小而频繁：今天补一篇会议纪要，明天改一段笔记，周末再导入几篇 PDF。如果每次都全量重建，既浪费时间，也没必要。系统把“文档内容是否变化”交给内容 Hash 判断，把“索引是否变化”交给全局版本号管理。

## 2. 文档身份与 Hash

每个文档有两个关键标识：

- `source_key`：稳定来源键。示例文档使用 `sample:相对路径`，上传文件使用 `upload:文件名`。
- `sha256`：文件原始字节的 SHA-256。

`source_key` 决定“这是不是同一篇文档”，`sha256` 决定“内容有没有变”。同步流程如下：

1. 计算新文件的 SHA-256。
2. 按 source_key 查找已有文档。
3. Hash 相同且状态为 ready：直接返回 unchanged，不解析、不嵌入。
4. Hash 不同或强制重建：重新解析，生成新 chunk 和新向量。
5. 新文档：分配稳定 doc_id，走完整索引流程。

doc_id 由 source_key 的散列生成，因此同一来源重复上传不会产生多篇重复文档。

## 3. 更新与删除

更新文档时，系统先比较新文件与旧文档记录的 SHA-256：相同就跳过，不同才重新解析、切块和嵌入。确认需要更新后，在一个 SQLite 事务中替换该文档的全部 chunk，然后：

1. 增加全局索引版本 index_version；
2. 删除旧向量并按 doc_id 写入新向量；
3. 从 SQLite 重新构建 BM25 快照；
4. 清理旧版本的语义缓存。

删除文档时，先删除向量，再删除文档记录（chunk 由外键级联删除），最后同样提升版本号并重建 BM25。

BM25 使用内存快照 + 原子替换，查询过程中不会看到“删了一半”的索引。向量写入失败时，文档仍保留在 SQLite 中，BM25 检索依然可用，系统会提示执行“修复向量索引”。

## 4. 为什么版本号这么重要

索引版本号是所有缓存的命名空间。版本号一变：

- 精确缓存 key 中的版本号变化，旧答案自然失效；
- 语义缓存按 version 字段过滤，旧向量不会被召回；
- 前端可以看到当前索引版本，判断知识库是否已更新。

这避免了“文档已经改了，但缓存还在返回旧答案”的经典问题。

## 5. 分层缓存

系统有三层缓存：

| 层级 | 存储 | 键 | 作用 |
| --- | --- | --- | --- |
| L1 | 进程内 | embedding 文本 Hash | 避免同一文本重复向量化 |
| L2 | SQLite | 问题归一化 + 参数 + 版本 | 精确命中原问题 |
| L3 | SQLite + 向量 | 问题 embedding 相似度 | 命中同义改写的问法 |

语义缓存的相似度阈值默认 0.94。只有置信度不低于 0.4 的回答才会写入，避免把低质量答案缓存下来。缓存命中时仍会写入一条新的 assistant 消息，保证会话历史完整。

## 6. 热更新的边界

当前实现是“文档级增量、索引级重建”：

- 新增/修改/删除一篇文档，不需要重新解析其他文档；
- BM25 会从全部 chunk 重建，个人知识库规模下耗时可以接受；
- 向量库按 doc_id 增量写入，不做全量重建。

如果未来 chunk 数量达到十万级，可以把 BM25 改成增量 posting list，或者按文档分片构建索引。当前选择优先保证正确性和可维护性。

## 7. 一致性检查

启动时会检查三件事：BM25 缓存版本是否匹配、embedding 模型签名是否变化、向量数量是否等于 chunk 数量。任意一项不一致都会触发向量修复。修复过程会重新嵌入全部 chunk，但不会重新解析原始文件，因此比重建整库更快。
