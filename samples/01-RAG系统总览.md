# 多模态 RAG 系统总览

## 1. 项目目标

知屿是一个面向个人知识管理场景的多模态 RAG 问答系统。它把散落在 PDF、Markdown、图片和纯文本里的资料，整理成可检索、可引用、可评测的知识库。系统不追求“大而全”的企业平台，而是优先保证三件事：资料找得到、回答有出处、更新足够快。

核心使用路径只有两条：离线把资料变成索引，在线把问题变成带引用的答案。离线索引的标准流程是：解析 → 清洗 → 切块 → 元数据绑定 → 向量化 → 建索引，同时写入 Chroma 与 BM25；在线问答则按需召回、重排和核查引用。所有工程优化都围绕这两条路径展开。

## 2. 技术栈

| 层次 | 选型 | 作用 |
| --- | --- | --- |
| 应用层 | FastAPI + Pydantic | 提供 REST、SSE 流式接口和 OpenAPI 文档 |
| 编排层 | 自研 Agent + LangChain 文本切分 | 查询分析、路由、检索、重排、引用核查 |
| 检索层 | Chroma + BM25 + RRF | 稠密向量召回与稀疏关键词召回融合 |
| 解析层 | PyMuPDF、Markdown AST、RapidOCR、VLM | 处理 PDF、Markdown、图片等多模态知识源 |
| 评测层 | RAGAS 风格指标 + Hit/MRR/nDCG | 检索与生成联合评估 |
| 存储层 | SQLite + Chroma | 元数据、会话、缓存与向量持久化 |

## 3. 离线索引链路

离线链路按“解析 → 清洗 → 切块 → 向量化 → 建索引”执行：

1. **解析**：根据文件后缀选择解析器。PDF 提取页面文本、表格和图片，扫描页渲染后走 OCR/VLM；Markdown 保留标题层级、代码块和表格；图片直接做 OCR 与视觉描述。
2. **清洗**：统一全角半角、去掉页眉页脚和孤立页码、合并重复空行，同时保留段落结构。
3. **切块**：优先按标题层级组织 section，再使用递归字符切分，默认 chunk_size 为 720 字符、overlap 为 120 字符。代码块和表格尽量保持完整。
4. **元数据绑定**：每个 chunk 记录文档 id、文档名、页码、标题路径、内容类型和 token 估算，供引用展示和过滤使用。
5. **建索引**：同一批 chunk 同时写入 Chroma 稠密索引和 BM25 稀疏索引，并记录索引版本。

## 4. 在线问答链路

在线链路是一个可观测的 Agent 流程：

- **查询理解**：结合最近对话做指代消解，判断意图是知识问答、寒暄、知识库统计、总结还是对比，并生成 1 到 3 个检索子问题。
- **多路召回**：每个查询分别走向量检索和 BM25 检索，使用倒数排名融合（RRF）合并。
- **重排**：用模型或启发式规则对候选片段重新打分，保留最相关的前 6 个片段。
- **上下文拼装**：按 token 预算选择片段，必要时补全相邻 chunk，并生成 `[1]`、`[2]` 形式的引用编号。
- **生成与核查**：只允许模型基于资料回答，回答后用引用核查器逐句检查引用是否真的有原文支持。
- **低置信度兜底**：当检索置信度或引用支持度不足时，触发一次 HyDE 二次检索，扩大召回并重新生成。

## 5. 存储与模块边界

SQLite 是元数据的唯一事实来源，保存文档、chunk、会话、消息、缓存和评测记录。Chroma 只保存向量和少量过滤字段；如果向量索引损坏，可以从 SQLite 中的 chunk 重新构建。BM25 使用内存快照，索引变更时原子替换，查询不会读到半成品。

解析、切块、向量化、查询改写、重排、缓存都被拆成独立模块，通过构造函数注入依赖。这样做的好处是：替换 embedding 模型或向量库时，不需要改 Agent 流程；新增一种文件格式时，只需要增加 loader。

## 6. 关键指标与取舍

系统关注四类指标：检索的 Hit@5、MRR@5，生成的 faithfulness、answer relevancy，引用的 coverage/accuracy，以及端到端 p95 延迟。个人知识库通常只有几百到几千个 chunk，因此优先选择“可解释、可修复”的方案，而不是引入过重的分布式组件。

在离线模式下，系统使用本地 hash embedding 和抽取式回答，保证没有 API Key 也能完整演示；配置在线模型后，查询分析、重排和生成会自动切换到模型版本。
